## 1. Motivación y Visión

**Regla de verdad que este incremento hace cumplir:** **producción es PostgreSQL y Cloudflare R2; SQLite existe únicamente como motor de pruebas y de desarrollo local.** Hoy la documentación, la configuración y el código afirman simultáneamente lo contrario.

### 1.1. Desfase de esquema PostgreSQL (bloqueante — parcialmente resuelto)

`LudekaDbContext` declara **31 `DbSet`** (`LudekaDbContext.cs:8-38`) pero la única migración existente creaba **27 tablas**. Faltaban:

- `BggCatalogStaging` (`:35`)
- `SocialInboxItems` (`:36`)
- `MonitoredSocialAccounts` (`:37`)
- `GamePriceSnapshots` (`:38`)
- y las columnas `BackCoverImageUrl` y `TableImageUrl` de `Games` (`Core/Entities/Game.cs:24-25`), además de `BggDiscoveryCount` en `NightlyCatalogingExecutionLogs`.

Como `Program.cs:329-332` ejecuta `MigrateAsync()` en Npgsql, **producción arrancaba con un esquema incompleto**.

**Ya entregado en este incremento:** migración `20260915100112_AddBggStagingSocialInboxPriceRadarAndGameImages` que añade las 4 tablas, las 2 columnas de `Games` y `BggDiscoveryCount`, con SQL PostgreSQL verificado (`timestamp with time zone`, `uuid`, `GENERATED BY DEFAULT AS IDENTITY`).

### 1.2. El esquema SQL de Supabase es falso

`docs/database/supabase_schema.sql` se autodeclara esquema maestro pero contradice al modelo real:

- Le faltan las mismas 4 tablas.
- Nombra mal una tabla: `"CommunityNotificationLogs"` (`:273`) cuando el modelo y la migración usan `"NotificationLogs"`.
- `GamePlayLogs` conserva `IsWon`/`PlayerScore` (`:74-75`), que no existen en la entidad.
- `UserPreferences` usa `PreferredCountry`/`Theme`/`CreatedAt` (`:289-291`) frente a `PreferredTheme`/`Country`/`UpdatedAt`.
- `GameIssueReports` (`:299-304`), `GameEditLogs` (`:315-319`), `Publishers` (`:331-333`), `Creators` (`:341-343`), `Stores` (`:354`), `ExpansionRecipes` (`:264-267`), `NightlyCatalogingExecutionLogs` (`:417-423`) e `InstagramPostDrafts` (`:434-440`) tienen columnas obsoletas o ausentes.
- `Games.BggId` es nullable (`:15`) cuando la entidad lo exige único no nulo.

Ejecutar ese script a mano produce un esquema **incompatible** con EF Core.

### 1.3. El fallback de medios guarda en memoria, no en disco

`Program.cs:158-166` decide la implementación así:

```csharp
if (options.HasValidCredentials) return CloudflareR2StorageService;
return SimulatedImageStorageService;   // ← siempre esto si no hay credenciales
```

- `SimulatedImageStorageService` (`Infrastructure/Services/SimulatedImageStorageService.cs:19-208`) guarda en un `ConcurrentDictionary` **en memoria** (`:24`). Reiniciar el contenedor borra todo.
- `PhysicalFileImageStorageService` **está registrado** (`Program.cs:157`) y sí escribe en disco (`wwwroot/images/games`, `:33-34,80-83`), pero **nunca se selecciona**.
- El workflow de Cloud Run (`.github/workflows/ci-cd.yml:103-118`) **no inyecta ninguna variable `Cloudflare__*`**, y `appsettings.json:88-95` tiene `Simulate: true`. Por tanto, en producción las imágenes van a memoria.

### 1.4. Fallback silencioso a SQLite en el contenedor

`Dockerfile:52` fija `ConnectionStrings__DefaultConnection="Data Source=/app/data/ludeka.db"` como valor por defecto de la imagen. Si el secreto de Cloud Run no llega, la aplicación **no falla: arranca con SQLite efímero** y crea un esquema local vacío. Es un fallo silencioso que enmascara un error de configuración.

### 1.5. Health checks que mienten

- `SqliteDatabaseHealthCheck` (`Health/HealthCheck` → `Web/Health/SqliteDatabaseHealthCheck.cs:23,34,37,41`) funciona contra cualquier proveedor, pero sus mensajes y su metadato `"provider": "Microsoft.EntityFrameworkCore.Sqlite"` están **codificados a SQLite**. En producción con PostgreSQL, `/ready` reportaría `provider: Sqlite`.
- `StorageHealthCheck` (`Web/Health/StorageHealthCheck.cs:20-22`) parsea `Data Source=` de la cadena de conexión. Con PostgreSQL no hay `Data Source=`, así que cae al valor `"ludeka.db"` y sondea el directorio de la aplicación en el contenedor. Mide algo real, pero **no lo que promete**: no verifica el almacenamiento de medios.
- Cloud Run no configura `/ready` como *readiness probe*; el workflow solo pasa flags generales.

## 2. Objetivos y Alcance Técnico

### 2.1. Esquema PostgreSQL canónico

- La migración `20260915100112_AddBggStagingSocialInboxPriceRadarAndGameImages` es la fuente de verdad del esquema.
- `docs/database/supabase_schema.sql` **deja de ser esquema maestro**: se regenera desde `dotnet ef migrations script` o se marca explícitamente como obsoleto y no ejecutable a mano.
- Verificación obligatoria contra una base Supabase de *staging*: `__EFMigrationsHistory` con las dos migraciones y las 31 tablas presentes.

### 2.2. Selección de almacenamiento de medios con precedencia explícita

Nueva lógica de selección, sustituyendo `Program.cs:158-166`:

1. **R2 válido** (`HasValidCredentials == true`) → `CloudflareR2StorageService`. Es el camino de producción.
2. **Sin R2 pero con ruta local configurada** → `PhysicalFileImageStorageService`, escribiendo en `Media__LocalStoragePath`. Es el camino de desarrollo y pruebas manuales: **persiste en disco**, no en memoria.
3. **Solo en entorno de pruebas** → `SimulatedImageStorageService`.

Reglas adicionales:

- Si `ASPNETCORE_ENVIRONMENT=Production` y R2 no está configurado, se emite un **log de advertencia explícito** al arrancar y `/ready` lo refleja. El objetivo es que la degradación sea visible, nunca silenciosa.
- La ruta local se sirve mediante el middleware de ficheros estáticos ya existente, manteniendo el mismo contrato `IImageStorageService`.

### 2.3. Eliminar el fallback silencioso a SQLite

- `Dockerfile:52` deja de fijar una cadena de conexión SQLite como valor por defecto de la imagen.
- Si en `Production` no hay proveedor PostgreSQL resoluble, la aplicación **debe fallar al arrancar** con un mensaje explícito, en lugar de crear una base SQLite efímera.
- `docker-compose.yml` y `docker-compose.staging.yml` pasan a declararse explícitamente como entorno **local**, con SQLite rotulado como tal, no como opción de producción.

### 2.4. Health checks fieles al proveedor

- `SqliteDatabaseHealthCheck` se renombra y reporta el proveedor real efectivo (`Npgsql` o `Sqlite`) en su metadato y sus mensajes.
- `StorageHealthCheck` verifica el **almacenamiento de medios configurado**: presencia de credenciales R2 o escritura real en `Media__LocalStoragePath`, en lugar de inferir un directorio desde `Data Source=`.
- Cloud Run configura `/healthz` como *liveness* y `/ready` como *readiness*, con el workflow actualizado.

### 2.5. Corrección documental: una sola verdad

- `docs/deployment/DEPLOYMENT_GUIDE.md` se reescribe como **guía de producción PostgreSQL**: conexión Supabase, migraciones EF, `scripts/supabase-backup.ps1` (`scripts/supabase-backup.ps1:23`) y verificación con `/ready`.
- `docs/specs/sistema/09-arquitectura-y-despliegue.md:4,14,58,68` y `docs/specs/sistema/README.md:16` pasan a describir PostgreSQL como persistencia de producción.
- SQLite queda documentado **exclusivamente** como motor de pruebas y de desarrollo local.
- Se unifica la cifra de pruebas con el número real medido tras ejecutar la suite, eliminando el "887" frente al "1.005".
- `docs/specs/ROADMAP_MVP_SLICES.md:152-155` deja de presentar SQLite y sus backups como operación de producción.

### 2.6. Pasos operativos de persistencia (entregable del incremento)

**Producción — Cloudflare R2**

1. Crear el bucket `ludeka-media` en Cloudflare R2.
2. Crear un token de API R2 con permiso *Object Read & Write* limitado a ese bucket.
3. Anotar el *Account ID* de Cloudflare.
4. Configurar un dominio público o subdominio `r2.dev` para el bucket y fijarlo en `Cloudflare__PublicCdnBaseUrl`.
5. Guardar en Google Secret Manager: `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`.
6. Inyectar en Cloud Run:
   ```
   Cloudflare__AccountId / Cloudflare__AccessKeyId / Cloudflare__SecretAccessKey
   Cloudflare__BucketName=ludeka-media
   Cloudflare__PublicCdnBaseUrl=<dominio>
   Cloudflare__Simulate=false
   ```
7. Verificar con una subida real y comprobar el objeto en el bucket.

**Local y pruebas — fallback en disco**

1. Dejar `Cloudflare__Simulate=true` (o credenciales vacías).
2. Definir `Media__LocalStoragePath` apuntando a un directorio del repo.
3. Las pruebas automáticas usan almacenamiento en memoria o un directorio temporal.

### 2.7. Pruebas (Strict TDD activo)

- Runner contractual: `dotnet test Ludeka.sln`.
- Test de precedencia: con credenciales R2 → R2; sin credenciales y con ruta local → disco; sin ninguna → memoria.
- Test de arranque: en `Production` sin PostgreSQL resoluble, el arranque falla con error explícito.
- Test de persistencia: una imagen escrita con el fallback local sobrevive a la recreación de la instancia del servicio.
- Test de health check: el metadato del proveedor reportado coincide con el proveedor real configurado.
- Test de esquema: el modelo EF no tiene entidades sin migración aplicable (comparación entre `DbSet` y migraciones).

## 3. Decisiones pendientes para el maintainer

1. **SQLite en desarrollo local.** Se propone mantener SQLite para desarrollo local y pruebas (rápido, sin contenedor) y PostgreSQL solo en producción y *staging*. Alternativa estricta: PostgreSQL también en local mediante un servicio en `docker-compose.yml`, con SQLite reservado exclusivamente a tests automatizados.
2. **`docs/database/supabase_schema.sql`.** Se propone regenerarlo desde las migraciones EF y declararlo derivado, no maestro. Alternativa: eliminarlo, porque `MigrateAsync()` ya crea el esquema.
3. **Backups.** Se propone `scripts/supabase-backup.ps1` como único procedimiento de producción y **retirar** `deploy/backup-sqlite.sh`, `deploy/backup-sqlite.ps1` y `deploy/restore-sqlite.sh` de la documentación de producción, conservándolos solo para desarrollo local.
4. **`docker-compose.staging.yml`.** Se propone que *staging* use PostgreSQL, para que sea un ensayo real de producción. Alternativa: dejarlo en SQLite como entorno local ampliado.

## 4. Criterios de Aceptación y Verificación

1. Una instancia recién desplegada crea **las 31 tablas** en Supabase y `__EFMigrationsHistory` contiene ambas migraciones.
2. `docs/database/supabase_schema.sql` ya no contradice al modelo (regenerado o marcado obsoleto).
3. En producción, una imagen subida persiste tras reiniciar el contenedor.
4. En desarrollo, el fallback local escribe realmente en disco y la imagen se sirve por HTTP.
5. Con `ASPNETCORE_ENVIRONMENT=Production` y sin cadena PostgreSQL, el arranque falla de forma explícita y visible.
6. `/ready` reporta el proveedor de base de datos real y el estado del almacenamiento de medios configurado.
7. Ningún documento del repositorio afirma que producción use SQLite.
8. Suite completa en verde con `dotnet test Ludeka.sln`.

## 5. Riesgos

| Riesgo | Impacto | Mitigación |
|---|---|---|
| Migración sobre una base con datos | Alto: pérdida de datos | Solo añade tablas y columnas anulables o con valor por defecto; sin `DROP` en `Up()` |
| Regenerar `supabase_schema.sql` puede inducir a ejecutarlo a mano | Medio | Declararlo derivado y desaconsejar su ejecución manual frente a `MigrateAsync()` |
| Retirar el default SQLite del `Dockerfile` rompe `docker run` sin variables | Bajo | Documentar el arranque local con `docker-compose.yml`, que sí provee la configuración |
| El fallback a disco en contenedores sin volumen se pierde al recrear | Medio | El fallback local es para desarrollo; producción exige R2 y se verifica en `/ready` |
| Cambiar los health checks altera la semántica de *readiness* | Medio | Mantener `/healthz` sin dependencias y mover toda verificación a `/ready` |
